# mike-cli

## Работа
- Вся работа ведётся в `.cases/`. Начни с `./bin/mike` — он печатает, где дело стоит и что дальше; правила — `.cases/RULES.md`.
- README / TODO / JOURNAL дела пишутся только через `./bin/mike` (`mike help` — примеры). Правка руками ловится отпечатком.
- Упёрся — сначала `.howto/` (рецепты, первая строка `when:` — слова беды) и `scripts/`, потом решай сам.

## Код
- Весь код — English целиком: имена, комментарии, docstring, сообщения вывода. Русский — только в описаниях для человека (README, журнал, рецепты).

## Память
- **Ничего не сохранять во внутреннюю auto-memory** (`~/.claude/projects/.../memory/`). Не создавать там файлов, не писать в `MEMORY.md`.
- Всё, что нужно помнить между сессиями, живёт в этом репозитории — в файлах проекта, которые видит любой агент (Claude Code, Codex).

## Feedback от агентов — что они просят и как пользуются mike
Отзывы приходят в `feedback/` — их пишут агенты командой `mike feedback` из своих дел (MLE, BibleTruck, legacy-дело от 08-27). Разбор каждого: причина → правка в коде + регрессия в `tests/` + PROBLEM/DECISION/RESULT в журнал дела → разобранный файл удалить из `feedback/` → наблюдение о поведении агента дописать строкой в список ниже. Список — чтобы проектировать под то, как агенты работают на самом деле, а не как задумано; обновлять при каждом разборе.

- **Исполняет напечатанное буквально**: путь, команду, совет из `Order`. Мёртвый указатель → гадает правила; разрушительный совет («merge or delete») → портит работу или перестаёт читать блок. Каждая строка вывода обязана разрешаться и иметь честную починку.
- **Читает исходники mike как документацию** (в отзывах — `commands.py:131`) и находит состояния, до которых нет команды. Docstrings и комментарии — часть интерфейса, держать правдивыми.
- **Приходит с чужим или старым делом** и упирается в отказ (`TODO.md is not parsable`) — без recovery-команды это тупик. Каждая ошибка: код выхода + что сделать (`mike migrate`, `mike doctor`, `mike help errors`).
- **Много правит TODO** (`edit/move/drop/hold`) и переписывал README целиком, пока не появились `readme set/add/drop`. Журнал засорял автозаписями правок — правка не событие (P5), историю держит git.
- **Пишет много файлов в `docs/`** — это deliverables (сценарии звонков, план в совет, контакты), не заметки. Лимит папки по байтам их не отличал от воды — снят; дубликат — по дословным фразам, не по общему словарю.
- **Называет вещи как видит**: `--phase p1` / `1` / имя фазы, дата в имени дела, событие длиннее 200 знаков. Формы принимать шире, канон держать внутри (pN, разбиение на заголовок + тело).
- **Планирует наперёд**: дедлайн вне текущей фазы (совет 13 сентября при незакрытых звонках) — нужна planned-фаза (`phase plan`), иначе работа ложится в чужую фазу или выпадает из TODO.
- **Не читает правила целиком**: знание — дозами в момент нужды (`mike help <topic>`), привычки — пять строк в CLAUDE.md проекта (INSTALL.md §3).
- **Проверяет себя `mike check` и верит нулю**: `cases: 0` должен кричать, а не зеленеть; `check` без фокуса на дело — шум.
- **Командует пачкой по номерам, которые только что прочитал**: `todo move` перенумеровывает фазу, и второй move в пачке целит в устаревший номер. Молчаливая подгонка («поставил в конец» словами точного перемещения) = неверный порядок с верой в успех → вне диапазона отказывать с готовой командой, не подгонять.
